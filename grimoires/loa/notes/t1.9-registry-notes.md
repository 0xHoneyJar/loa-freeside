## The four-axis tenant ownership (per `[[gateway-as-registry]]`)

| Axis | Field | Source |
|------|-------|--------|
| **A (registry policy)** | `slug`, `upstream`, `visibility`, `access`, `status` | tenants.ts (curator-owned) |
| **B (upstream broadcast)** | `name`, `description`, `publisher`, `auth`, `authHeader`, `capabilities`, `pricing`, `owner`, `documentation` | tenants.ts as v0.2 FALLBACK; will be replaced by upstream beacon broadcast in v0.3 |

The gateway is a registry, not a vault: identity-api **announces** its own
auth requirement (`auth: "api-key"`, `authHeader: "X-MCP-Key"`); the gateway
transcribes the declaration into the federation manifest and forwards the
header — it never holds identity-api's secrets. The caller supplies its own
`MCP_IDENTITY_UPSTREAM_KEY` (the `credentials_ref.key` declared in the
building's `beacon.yaml`).

## MCP endpoint placeholder strategy

`upstream: "https://identity-api-production.up.railway.app"` — projected
Railway production hostname (matches the `score` tenant pattern:
`score-api-production.up.railway.app`). The actual emitted hostname is
finalized at first Railway deploy; if Railway emits a different production
URL the operator must update this field. Documented inline in the tenant
entry as `TODO: confirm at deploy time`.

The v0.3 broadcast layer (per tenants.ts header comment) will replace most
fields with values fetched from `/.well-known/mcp.json` on the upstream;
at that point the operator-supplied `upstream` becomes the only required
field and broadcast handles the rest.

## Beacon cross-check (slug/is/is_not/composes_with verbatim)

The registry yaml's schema does NOT carry `is`/`is_not`/`composes_with`
fields — those live in the **beacon** at
`/Users/zksoju/Documents/GitHub/freeside-auth/packages/protocol/beacon.yaml`.
The registry is the lightweight pointer; the beacon is the contract. This
matches every existing entry (sonar-api, inventory-api, etc.) — they all
just point to a beacon URL plus carry visibility/rename metadata.

Verbatim cross-check of the building's beacon.yaml (T1.8 output):

| Field | beacon.yaml | registry.yaml |
|-------|-------------|---------------|
| slug | `"identity-api"` | `identity-api:` (matches) |
| publisher | `"0xHoneyJar"` | n/a (registry uses `owner: 0xHoneyJar` instead) |
| `is.one_liner` | "Central identity SoR..." | n/a (lives in beacon; surfaces via `freeside-cli catalog`) |
| `is_not[]` | 4 entries (no chain indexing, no per-world content, no Dynamic, no client UI) | n/a (lives in beacon) |
| `composes_with` | inventory-api/score-api/codex | n/a (lives in beacon) |
| `cycle_state.status` | `candidate` | n/a (lives in beacon) |
| `mcp.tools` | `[resolveByWallet, getProfile, getMiberaDimensions]` | n/a (lives in beacon; gateway tenant.capabilities only carries MCP capability classes: `["tools"]`) |

The gateway tenant's `capabilities: ["tools"]` is the **MCP capability
class** (per the MCP spec — `tools` vs `resources` vs `prompts`), not the
list of tool method names. The beacon's `mcp.tools[]` is the per-method
list (the 3 unauthenticated read-tools per T1.8 audit).
