## 1. Problem & Vision

**Problem.** Community onboarding is fragmented (Discord invite vs website vs future, no shared
state); presentation/onboarding logic risks being trapped *inside* the bot (which should only
execute); and the doctrine's centerpiece — the shadow "what-would-change" comparison — exists only
as mock HTML in zero of five services (KEEPER/WEAVER). A CM arrives mid-anxiety, already running
Collab.Land, wanting one guarantee — *"this bot won't touch my roles until I'm sure"* — and the
payoff is empty.

**Vision.** Shadow is a **universal preview/diff primitive**: for any feature whose effect you can
*consume or mock*, compute proposed, render **current → proposed** as an animated before/after, and
apply only behind an explicit, **substrate-enforced** gate (brief §1). The substrate is a
**resumable, medium-agnostic state machine** owned + *distributed* by worlds-api; entry surfaces are
thin lenses. Cohesion is a consequence of one substrate (brief §4).

**The reveal (Phase 2).** The "after" surfaces **qualified wallets who haven't joined the Discord**,
with numbers — shadow becomes **growth intelligence** ("N wallets qualify for [role], not in your
server"). The CM came for community management and discovers **latent community + leads**.

**Why now.** The other Freeside APIs are laid; verify-message WYSIWYG preview already proves the
primitive; this cycle generalizes it and proves **1→2 scale** (Mibera → +Purupuru).

## 4. Functional Requirements

- **FR-1 · Medium-agnostic entry.** A CM may enter from **website** or **Discord invite link**; each surface fires transition *events* into the worlds-api state machine.
- **FR-2 · Resumable cross-medium state.** State persists per **(CM identity × world)** — a **stable identity key resolved via identity-api** (FL-HC2). *When* a CM switches website↔Discord mid-onboarding, *the system shall* resume at the current state. **Failure/recovery semantics (FL-HC6):** the PRD constrains required behavior for (a) identity-link failure — onboarding blocks with a clear "link your identity" state, never silently forks; (b) identity-api/config outage — the machine reports a recoverable `degraded` state and resumes on recovery; no partial/ambiguous state is persisted.
- **FR-3 · Substrate-enforced shadow gate.** State `apply_mode ∈ {SHADOW, LIVE}` per world, **default SHADOW**. The gate is **enforced in the substrate, not the consumer (FL-B1/B6):** the transition/`RoleWriter` core **rejects any role write/create when `apply_mode == SHADOW`** and emits an ACVP-envelope audit event on the rejection. Tests MUST prove no concrete live writer is reachable in shadow.
- **FR-4 · Role MVP (shadow-first).** Role **assignment + creation + scaffolding**: the substrate proposes assignments **and** new roles to create / a structure to scaffold, previewed in shadow; applied only on go-live.
- **FR-5 · Before/after comparison.** **BEFORE** = current roles → **AFTER** = proposed roles for current members **+ latent qualified members (numbers)**, with **motion**. One medium-agnostic substrate, two render targets (web DOM + Discord CV2). **MVP picks ONE primary render target for acceptance** (FL-HC7; §6).
- **FR-6 · Latent-member / leads surface.** "After" includes **qualified-but-not-joined** wallets with counts. **MVP: mocked** (mock-as-shadow-input); real numbers depend on cross-service data (Deps; score-api gaps → issues).
- **FR-7 · go_live guard (precise).** **Role-map version = a content hash** over {role rules, scaffolding config, relevant world config, roster-snapshot metadata} (FL-B7). **HARD guard:** `SHADOW → LIVE` requires a discrepancy report whose hash **matches the current role-map hash** (a stale report against a changed map → `GuardFailed`). The PRD defines what invalidates a report (roster/config/role-rule change). **The 2-week soak is a SOFT advisory, NOT a GuardFailed** (FL-B9) — surfaced as a recommendation, never a lock.
- **FR-8 · Distributed pure substrate + gated writer.** worlds-api distributes (git-source, SHA-pinned) the pure Effect core: `transition`, guards, `computeProposed`, `diff/discrepancy`. **Ports `RosterSource` + `RoleWriter` are Effect `Layer`s** the actor supplies — **mock Layer = shadow; live Layer = apply** (the mock↔live switch). The `RoleWriter` is **gate-checked**: it receives `apply_mode` and emits auditable write-intent / write-result events. A **stub exported-symbol table** ships with the package to clarify the seam (FL-HC5).
- **FR-9 · Rollback, coexistence, scaffolded-role lifecycle.** `LIVE → SHADOW` instant + always allowed. **Collab.Land coexistence mechanism (FL-B3):** Freeside manages only a **namespaced role set** (a Freeside prefix / explicit ID set) **OR** requires the CM to explicitly hand off specific roles from Collab.Land before LIVE — never silently contend. **Scaffolded-role rollback (FL-B8):** rollback **halts assignments and LEAVES created roles intact, with a warning** (non-destructive default — deleting created roles on rollback could strip users); destructive teardown is an explicit separate action, never automatic.
- **FR-10 · MVP authorization floor (NEW — flatline scope change, FL-B2/B4/B5/HC3).** State guards are not enough — **go-live and all writes require an *actor* guard.** MVP floor: the CM identity must be **authorized for the target world** (admin allowlist + Discord guild owner/admin verification where available + scoped write token). The **config-seam write-auth verifies CM-identity-scoped authorization — NOT "any bearer"** — even as a stub that checks the identity-api token against the world's managed set, *before* the substrate is distributed or any go-live is permitted. Full `managed-worlds` route is the scale path; the floor is mandatory for MVP because go-live writes to a real server.

```
SHADOW = a diff-lens over any feature you can consume-or-mock
  current  = consume(live | mock) ─┐
  proposed = computeProposed(cfg) ─┼─▶ diff ─lens(motion)─▶ before→after (+ latent members)
                                    │                            │
                                    ▼              apply_mode==LIVE  AND  CM authorized ← TWO gates
                                                   gate-checked RoleWriter → create + assign (audited)
```

## 5. Technical & Non-Functional

- **NFR-1 · Ownership/distribution.** worlds-api owns; sovereign git-source (SHA-pinned), no npm registry; consumers don't re-implement (governor/speaker).
- **NFR-2 · EffectTS.** Typed states/transitions/errors; illegal transitions fail loud (typed `GuardFailed`); pure functions have no I/O (injected as `Layer`s).
- **NFR-3 · ACVP-shaped / verifiable.** Schema-verified transitions + events-traced; the invariant "side-effect ⇒ `apply_mode==LIVE` ∧ CM authorized" is **provable** (shadow ⇒ zero writes), enforced substrate-side.
- **NFR-4 · Cohesion-by-construction.** One substrate + pure projection ⇒ cohesion across media.
- **NFR-5 · Mock-as-shadow-input.** Features shadow/visualize on mocked data before real backends; live cutover is for *applying*.
- **NFR-6 · Persistence contract (FL-HC8).** Role-map + apply_mode + the resumable lifecycle state persist via the worlds-api config seam (`/v1/config/:world/:surface`) as versioned, optimistic-locked records. **The config-service is a HARD dependency for *apply/persist*** — the cutover (`CONFIG_SERVICE_URL`) must land before LIVE; shadow-preview may run on mock. A minimum-viable persistence contract (state record shape + version) is defined in the SDD so config-service is not a hidden late-failing dependency.
