## Problem

Labelling is scattered and operator-authored. "Which NFT collections exist and their
`{chain, contract, standard, world}`" is hand-typed in ≥5 places (shadow-audit's `COLLECTION_REGISTRY`
env, sonar `constants.ts`, dashboard's empty `CONTRACT_REGISTRY: {}`, worlds' `nft_contracts: []`),
making the **operator the integration bus for facts**. But the deeper truth (operator, 2026-07-03):
*"the worldline spine and labelling for entities … we've been doing for the user/member graph is
directly related to labelling of contract addresses as well. All of which should be queryable easily
by you just like /recall QMD for the vault. We are data and truth first — distilling from the bottom
up raw signals, refining it so it retains its quality so it can exist without the noise."*

Labelling members and labelling contracts is **one concern, one spine** — and we have that spine: the
hash-chained, Postgres-backed member-graph ledger built this session. It is not being used to label
contracts, and its entities are not agent-queryable the way the vault is.

> Sources: 2026-07-03-collections-sot-direction.md (+ §OPERATOR REFRAME); ml-sot-consumers map;
> operator reframe verbatim; the shadow-mode ledger built in PR #429.

## Vision

**One labelling substrate for every entity in the system, distilled bottom-up and queryable like the
vault.** The worldline spine (the shadow-mode hash-chained ledger) already distills raw signals into
labelled subjects (identity_user / discord_member / wallet_only). A **contract/collection is just
another labelled entity** on it. Raw signals at the bottom (belt Transfer stream, on-chain ERC-165,
discord/sonar) → the ledger's observation→subject reduction distills them, retaining quality and
shedding noise → the labelled entity carries derived + ratified labels with provenance → the agent
**queries it like /recall QMD queries the vault** (semantic + lexical, governed by the same
trust-weight/withhold plane). Collections is **instance #1**; the pattern generalizes to any entity.

**Keystone — PROVEN this session, zero operator input:** chain/contract/collection_key from belt
`TrackedHolder` (24); `token_standard` derived on-chain via ERC-165 — 20 erc721 + 4 erc1155, catching
the silently-wrong case. Full data: `grimoires/loa/context/self-grounded-collections-registry.txt`.

## Non-Goals

- **The pg-review UI / fullstack-native operator dashboard** — operator: *"really low priority, you
  can even ignore it."* The surface is agent-native query (G-3), not a human dashboard.
- A `collections` block in world.yaml + a separate pg projection — DROPPED by the reframe (the ledger
  is the single store; the flatline's dual-store tensions dissolve). worlds/onboarding stays the
  AUTHORITY for the world-membership label, stored as a ratified edge on the ledger, not a 2nd store.
- Unifying the member-graph and contract-labelling into one query index beyond exposing collections
  as a source — the FULL "everything queryable like /recall" is the direction; this cycle proves it
  with collections.
- sonar `constants.ts` / dashboard collapse — next cycle (trigger: SoT authoritative).
- A generic labelled-entity framework — reuse-shaped only.

## Users / Stakeholders

The operator (ratifies subjective labels; otherwise reads, doesn't author); agents (derive + query —
never ask); the sandwich-line shadow-audit deploy (first consumer); future Freeside customers
(their collections self-populate on onboarding); "us as inhabitants" (agents + humans) — the labelling
substrate is a public good.

## Functional Requirements

- **FR-1 (G-1, the entity on the spine):** add a `collection` SubjectKind to the shadow-mode protocol
  (`packages/protocol/shadow-mode/src/schemas/subject.ts`) — a labelled entity keyed by identity
  `(chain, contract)`, carrying labels `{token_standard, collection_key, world, role}` + provenance
  per label. Reuses the existing hash-chained ledger + PostgresLedgerStore (built this session): the
  entity lives on the worldline spine, so append-only history, tamper-evidence, and the freeze/verify
  machinery apply for free. The world-membership label is a ratified edge (EVANS invariant:
  one collection ↔ exactly one world; `(chain, contract)` unique). `collection_key` is the belt
  routing alias, NOT the identity.
- **FR-2 (G-2, distillation engine, agent-first):** a `freeside collections` verb group:
  - `sync` — READ-only: pull belt `TrackedHolder` (chain/contract/collection_key) + derive
    `token_standard` on-chain (ERC-165; `unknown` when un-derivable, never assume erc721) + propose
    world-binding (reverse `/v1/worlds/lookup` + key-prefix heuristic); print a ratifiable diff. Exit
    0 clean / non-zero on any un-ratified proposal (CI-usable).
  - `propose` — distill into born-low ledger entities (label provenance `ai-derived`,
    `read_state: unread`); subjective labels (world, role) blank + flagged.
  - `ratify <key>` — the operator's sign-off (FR-3).
  - **Hazard-handled:** `collection_key` normalized `_`→`-` for the event-schema grammar
    `/^[a-z][a-z0-9-]*$/` (`packages/events/src/schemas/nft-activity.ts`); the diff shows the transform.
- **FR-3 (G-2/G-1, ratification = the /recall force-chain, agent-never-self-ratifies):** derived
  labels are born `ai-derived`; the operator promotes to `operator-validated` with one gesture
  (skimmed-ok → sign → stake) — the exact /recall cockpit vocabulary, enforced by the
  `memory-promotion-guard` hook shape so the agent physically cannot self-ratify a subjective/ratified
  label. The agent re-derives + self-corrects DERIVED labels freely; NEVER flips a ratified one.
- **FR-4 (G-3, /recall-QMD-queryable):** labelled collection entities are exposed as an agent-queryable
  source — indexed for semantic + lexical retrieval and surfaced through the /recall governance plane
  (trust-weight by label provenance, withhold contested). Concretely: a query path
  (`freeside collections query <q>` and/or a QMD source registration) that returns ranked, provenance-
  badged entities. AC: "which collections are in mibera" and "who owns 0x6666…c420" both return the
  right entity with its trust badge, like a /recall hit.
- **FR-5 (G-4, settle gate — shadow-audit collapse):** shadow-audit's `loadRegistryFromEnv`
  (`bin/http.ts`) reads the labelled collection entities (via a ledger projection / query) instead of
  `COLLECTION_REGISTRY`; the env var becomes an optional deprecated override. Kill-test: boot
  shadow-audit with NO `COLLECTION_REGISTRY` and it serves `GET /v1/collections/:chain/:contract`
  correctly for the ratified set.
- **FR-6 (G-5, drift sensor):** `freeside collections drift` re-derives DERIVED labels (belt +
  on-chain), classifies `coherent | drifted | orphaned | unratified | unknown_standard`; drift on a
  ratified label → contested (never silent overwrite). CI/cron, fails loud.
- **FR-7 (G-6, reuse-shaping):** factor ingest→distill→ratify→query over a small labelled-entity shape
  (identity + derived-labels + subjective-labels + provenance) so a second entity kind supplies its
  own `ground()` + label-map and inherits the rest. No framework; no collections-hard-coding in the spine.

## Invariants (every FR must satisfy)

## Assumptions (falsifiable)

- [ASSUMPTION] a `collection` SubjectKind is an additive, non-breaking extension of the shadow-mode
  schema (the enum + a labels bag) — if it strains the member-oriented subject shape, collections get
  a sibling labelled-entity table on the same ledger/store instead of the same `subjects` table.
- [ASSUMPTION] the labelled entities can be registered as a /recall-QMD source (or a parallel index)
  without reworking the QMD backend — if QMD ingest is closed, FR-4 ships a dedicated
  `freeside collections query` (BM25 + optional vector) that mirrors the /recall register/governance.
- [ASSUMPTION] shadow-audit can read the ledger projection at boot without a fragile live dependency —
  else a build-time snapshot of the ratified set ships in-image (the role-snapshot precedent).

## Risks / Gates

- **R-1 (mostly in-repo now):** FR-1/FR-2/FR-3/FR-6 in loa-freeside (`shared/shadow-mode`) +
  freeside-cli; FR-5 in shadow-audit; FR-4 touches the /recall/QMD surface (`~/.claude` = System Zone —
  read-only; a collections query verb lives in-repo, not in .claude). The reframe REMOVED the
  worlds-api cross-repo dual-store; worlds/onboarding is a read-authority, not a write target.
- **R-2 (standard un-derivable):** legacy no-ERC-165 → `unknown` → ratify-only; the drift sensor
  classifies `unknown_standard`. Never assume.
- **R-3 (scope depth):** collections-as-a-ledger-entity + a query surface is deeper than a config file.
  Slice so G-1+G-2 (entity + distillation) land even if G-3 (full QMD query) reduces to a scoped
  lexical query; G-4 (shadow-audit collapse) is the settle gate and depends only on G-1/G-2.
- **R-4 (world-binding ambiguity):** `puru_*` → a purupuru world not on the deployment registry;
  propose flags it `unratified`/`orphaned`; operator ratifies the edge (or files the world). The
  ratify case, not a blocker.

## Flatline v2 integration (5 blocker-theme cures — requirement level; design detail → SDD)

- **Identity normalization (SKP-002a):** entity identity `(chain, contract)` is normalized ONCE at a
  single choke point — chain as a canonical numeric string, contract lowercased (reusing ordering's
  `normalizeContractAddress`/`normalizeChainId`, `packages/services/ordering/src/contract-address.ts`).
  No checksum-case identity, no aliasing on identity; `collection_key` is the only alias. The SDD
  pins the exact function + a normalization test as an AC.
- **QMD-vs-CLI scope (SKP-002b, IMP-004):** this cycle ships a **dedicated `freeside collections query`
  (lexical, provenance-badged, governed by the label trust-fields)** as the concrete FR-4 surface;
  registering the entities as a first-class /recall-QMD source (semantic + rerank parity) is the
  SHAPE it's built toward but a follow-up, not the settle gate. G-3 metric holds against the CLI query.
- **Ledger extension (SKP-001):** additive, backward-compatible — a new `collection` SubjectKind value
  + a per-kind labels bag; existing member subjects untouched (the enum widens, no column drops).
  Legacy rows read unchanged; the migration is one additive SQL. The SDD specifies the schema delta +
  a "member subjects still resolve" regression AC. Fallback (assumption): a sibling `labelled_entities`
  table on the same store if the `subjects` shape strains.
- **Ratification authorization (SKP-003):** NOT a new auth model — the /recall force-chain IS the
  authorization: a label flips `ai-derived → operator-validated` ONLY behind a fresh cockpit grant
  (the `memory-promotion-guard` hook shape), one grant = one write, TTL-bounded. The agent has no
  code path to self-ratify. Every ratify is an append-only provenance event on the hash-chained
  ledger (audit trail for free). The SDD specifies the grant mechanic + the provenance event.
- **Derived-vs-ratified drift policy (IMP-007):** DERIVED labels — the agent re-derives + overwrites
  freely (ground truth wins). RATIFIED labels — drift raises `contested`, never a silent overwrite;
  the operator re-ratifies or corrects. The SDD's drift table enumerates the five classes + the
  per-class action.
