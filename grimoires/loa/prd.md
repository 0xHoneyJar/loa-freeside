> **Cycle**: cycle-049 · codename `discovery-loop`

## 1. Problem Statement

The `freeside-*` building network has every part of a discovery system **scaffolded but inert**. Loa agents cannot navigate it the way they navigate constructs.

> From `user-description.md:8-12`: "the BeaconV3 schema exists, the registry has a hand-written skeleton, `freeside-cli list` works — but no building broadcasts a real beacon, no live endpoint serves the federation manifest, and the gateway is not wired to the registry. The loop `building declares → registry aggregates → endpoint serves → agent queries` has every part except the wiring that makes it run."

A second, structural problem: **schema and doctrine have diverged.** [ADR-008 §D-3](../../decisions/008-freeside-as-factory.md) canonized that buildings declare *belts* (`produces` + `consumes`), but the BeaconV3 schema shipped in PR #212 carries only `capabilities` and a loosely-defined `composes_with` — there is **no way for a building to declare its output belts**. Without `produces`, an agent can only find a building by name, never by capability ("who produces `wallet-scores`?").

> From `user-description.md:18-22`: "ADR-008 §D-3 canonized 'belts' but the schema never implemented them — schema and doctrine diverged."

> **Sources**: `user-description.md:1-37`, `decisions/008-freeside-as-factory.md` §D-3, confirmed Phase 0.

## 2. Goals & Success Metrics

| ID | Goal | Success Metric |
|----|------|----------------|
| **G-1** | A Loa agent can discover a `freeside-*` building by querying a live federation manifest, not by hardcoded knowledge | `/federation.json` is served live and returns ≥1 registered building with its belts + capabilities |
| **G-2** | A building can declare what it *produces* — discovery becomes capability-addressable, not name-addressable | BeaconV3 has first-class `produces` + `consumes` belt fields; a fixture beacon validates against the amended schema |
| **G-3** | The operator can inspect any registered building's beacon against live data | `freeside-cli inspect freeside-score` returns the validated BeaconV3 beacon fetched through the live manifest |
| **G-4** | BeaconV3 schema and ADR-008 §D-3 belt doctrine are reconciled — no divergence | `composes_with` removed; `produces`/`consumes` present; schema-version bumped; ADR-007 Appendix A spec matches the shipped schema |

**Operator-first metric** (the binding acceptance bar, Phase-0 gap answer): the discovery loop is provably closed *end-to-end against a `freeside-score` fixture beacon* — registry aggregates the fixture → `/federation.json` serves it → `freeside-cli inspect` returns it validated. Useful for the operator before any org-wide surfacing.

> **Sources**: `user-description.md:55-60`, Phase-0 gap answers (2026-05-19), `decisions/008-freeside-as-factory.md` §D-5.

## 4. Functional Requirements

### FR-1 — BeaconV3 belt fields (`packages/beacon-schema/`)

Amend the BeaconV3 sealed schema:

- Add `produces`: array of output belts — each with `belt` name, `schema` (JSON-schema path), `description`.
- Add `consumes`: array of input belts — each with `from` (sibling building slug), `belt` name, `tag` (`TagName@version+hash` per ADR-008 §D-8), `why`.
- **Remove `composes_with` entirely** (Phase-0 gap answer: hard-replace — `@freeside/beacon-schema` is v0.2.0, days old, zero external broadcasters; no migration window warranted).
- Schema-version bump on `@freeside/beacon-schema`.
- Update ADR-007 Appendix A spec ↔ the shipped schema so they match (G-4).

> Acceptance: when the schema changes, the BeaconV3 fixture set is updated and all schema tests pass.

### FR-2 — Live `/federation.json` endpoint (`packages/freeside-registry/`)

- A running HTTP endpoint serving the aggregated federation manifest.
- **Internal-only scope this cycle** (Phase-0 gap answer): serves all registered buildings without an auth-token gate, reachable by the operator. The ADR-008 §D-8 public-redaction tier + per-tenant authenticated tier are **deferred** (see §6 Out of Scope).
- Manifest content: per building — `slug`, `one_liner` (from `is`), `is_not`, `produces`, `consumes`, `capabilities`, `visibility`.
- Built on the existing `freeside-registry` manifest-builder (PR #213) + `registry.yaml`.

### FR-3 — Wire `apps/mcp-gateway/` to the registry

- The mcp-gateway consumes `packages/freeside-registry/` and serves the federation manifest at the gateway origin.
- Replaces / supersedes the gateway's current hand-encoded `tenants.ts` aggregation with the registry-driven path (or bridges them — `/architect` decides the exact seam).

### FR-4 — `freeside-cli inspect` + `doctor` functional (`packages/freeside-cli/`)

- `freeside-cli inspect <slug>` — fetch the building's beacon through the live manifest, validate against BeaconV3, pretty-print. (Currently stubbed — PR #213.)
- `freeside-cli doctor` — audit every registered beacon against BeaconV3; resolve Tag references; report compliance. Ships **functional**; the cycle's pass/fail gate is `inspect` per the acceptance bar, but `doctor` must run and exit clean on the fixture set.

### FR-5 — `freeside-score` fixture beacon (the test target)

- A fixture `beacon.yaml` for `freeside-score` lives in-repo (test fixtures).
- Declares: `produces` [`wallet-scores`, `rank-changes`, `factor-metadata`], `consumes` [`freeside-sonar` `chain-events`], `capabilities` (MCP tools), `visibility: internal`, `cycle_state.status: active`.
- This is the artifact the end-to-end loop test runs against. **The real `freeside-score` beacon in its own repo is OUT OF SCOPE** (§6).

### FR-6 — E2E validation task

A final sprint task asserting the closed loop: fixture beacon → registry aggregation → live `/federation.json` → `freeside-cli inspect freeside-score` returns the validated V3 beacon. Maps to the operator-first acceptance metric (G-1 + G-3).

> **Sources**: `user-description.md:16-37`, Phase-0 gap answers, `decisions/008-freeside-as-factory.md` §D-3/§D-5/§D-8, PR #212/#213 current state.

## 7. Risks & Dependencies

| Risk / Dependency | Severity | Mitigation |
|-------------------|----------|------------|
| Cross-repo dependency on `freeside-score` | Medium | Use an in-repo **fixture** beacon — the loop is provable without the cross-repo work (acceptance bar explicitly chose the fixture path). |
| Federation endpoint = network security surface | Medium | Internal-only scope this cycle (NFR-3); full review + audit rigor (NFR-4); public/auth tiers deferred with the surface explicitly named. |
| Breaking schema change (`composes_with` removal) | Low | Zero external broadcasters today (`@freeside/beacon-schema` v0.2.0); semver bump (NFR-5); only test fixtures consume it. |
| mcp-gateway has a pre-existing `tenants.ts` aggregation path | Low-Medium | `/architect` decides the seam — replace vs bridge. Flag as an SDD decision. |
| Cycle could sprawl into the deferred §D-8 tiers | Low | Out-of-scope table (§6) is explicit; review/audit gate on scope creep. |

> **Sources**: Phase-0 gap answers, `decisions/008-freeside-as-factory.md` §D-8/§D-10, mcp-gateway README (`apps/mcp-gateway/README.md` — `tenants.ts` v0.2→v0.3 transitional shape).

## 8. Acceptance Criteria

The cycle is **done** when:

1. BeaconV3 schema has `produces` + `consumes`, no `composes_with`, version-bumped, all schema tests green (G-2, G-4).
2. ADR-007 Appendix A spec is updated to match the shipped schema (G-4).
3. A `freeside-score` fixture beacon validates against the amended schema (FR-5).
4. `/federation.json` serves live, internal-scope, aggregating the fixture beacon (G-1, FR-2).
5. The mcp-gateway serves the registry-driven manifest (FR-3).
6. `freeside-cli inspect freeside-score` returns the validated V3 beacon fetched through the live manifest (G-3, FR-4).
7. `freeside-cli doctor` runs and exits clean on the fixture set (FR-4).
8. The FR-6 E2E test asserts the full loop and passes.
9. CI green: `path-domain-check` (network-only), schema tests, build.

## 9. Appendix A — Reference `freeside-score` beacon shape

The fixture beacon (FR-5) follows the design drafted 2026-05-19 — recorded here so `/architect` has the concrete target:

```yaml
schema_version: "3"
slug: freeside-score
is:
  one_liner: "Wallet + community scoring — activity events become rank/factor signals"
  scope: ["Compute conviction + behavioral scores from on-chain activity",
          "Maintain rank changes + factor metadata per wallet, per community",
          "Answer scoring queries via MCP tools + REST"]
is_not:
  - "Does NOT index chains — consumes freeside-sonar's event belt"
  - "Does NOT store NFT metadata — that is freeside-storage"
  - "Will NOT render UI — products built on score do that"
consumes:
  - from: freeside-sonar
    belt: chain-events
    tag: SonarPort@2.1.0+a3f2c891d4e8b7c2
    why: "raw transfer/holding events scoring is computed from"
produces:
  - belt: wallet-scores
    schema: packages/schema/wallet-score.schema.json
    description: "per-wallet conviction + behavioral score, updated on activity"
  - belt: rank-changes
    schema: packages/schema/rank-change.schema.json
    description: "rank-delta events emitted when a wallet's standing shifts"
  - belt: factor-metadata
    schema: packages/schema/factor.schema.json
    description: "the factor definitions that decompose a score"
capabilities:
  tools: [get_wallet_scorecard, get_zone_digest, list_factors,
          lookup_factor, get_top_movers, search_score_entities]
upstream: https://score.0xhoneyjar.xyz
auth: { kind: api-key, header: X-MCP-Key }
visibility: internal
pricing: { model: free, description: "free for first-party tenants" }
acvp_invariants:
  - id: event_completeness
    scope: "every consumed sonar event produces exactly one score recompute"
    proof_artifact: tests/acvp/event-completeness.test.ts
cycle_state: { status: active, since: "2026-05-03", next_review: "2026-08-03" }
```

> **Sources**: beacon design session 2026-05-19, `decisions/008-freeside-as-factory.md` Appendix A, mcp-gateway `tenants.ts` score-tool list.
